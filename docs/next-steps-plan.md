# 无痕对话插件后续推进计划

制定日期：2026-11-09。以本地 `main` 的 `794683d` 和现有测试记录为起点；每次开始执行前复查代码、安装版本与测试结果。本文是计划，不代表下面的待办已经完成。

## 目标与完成标准

做一个日常可用的 DSH 无痕对话：正常使用和删除后，不再从 DSH 的普通历史、会话存储和插件临时附件目录找到该对话的内容；异常退出后允许下次启动清理。附件使用期间可以暂存磁盘，正常删除算删除，不要求防止数据恢复。

无痕不意味着模型服务商收不到消息；手动 `@` 引用的原文件和工具对外部文件的修改，也不由本插件撤销。其他插件可能有独立的数据处理行为。对没有验证过的场景不作保证。

完成标志：同一个候选版本通过本计划 P0、P1 中适用的验收；普通会话对照正常；已知限制和支持的 DSH 版本写清；测试结果能追溯。不能把不同旧版本的通过记录拼成当前版本的完整通过。

## 当前基线

- 普通消息与草稿的无痕分流、附件临时目录和删除已有实现；图片、文本、拖放等在不同预览版做过实测。
- `794683d` 已加入无痕会话的额外日志字段保护并推送。上次 53 项自动测试通过；本机 DSH 的日志提供者和注册表用合成探针验证过，隔离 DSH 自检为 `sessionLog: ok`。
- 上述日志验证尚未覆盖真实桌面网络请求和子会话；该修复尚未安装到真实 desktop profile。真实安装版以开始执行时重新核对为准。
- 后台任务与附件删除时序、脱离任务的子进程、自检故障提示及当前候选版本的完整桌面回归仍有缺口。
- 已有测试清单：`docs/test-cases.md`。项目 `技能.md` 和旧 `docs/roadmap.md` 有历史内容，执行时以最新交接、代码和验证结果为准。

## P0：先确认额外日志保护真正生效

### 1. 核对当前状态并准备候选版本

- 查看 `git status`、代码提交、实际 DSH 版本及 desktop profile 引用的安装包；保留现有未提交修改。
- 给含本次修复的候选包使用新版本号，避免同版本 tgz 被依赖缓存复用、也避免混淆旧安装包。
- 运行 `npm test` 与 `node scripts/verify-session-log-installed.mjs`，记录结果和版本。

验收：构建内容可追溯到具体提交；自动测试通过；隔离验证中无痕字段缺失，普通对照存在。若失败，先定位问题，不继续宣称已保护。

### 2. 验证真实请求和子会话

- 优先在隔离 DSH_HOME 使用本地模拟服务或受控请求接收端，用合成探针分别发起普通和无痕对话。仅记录字段是否存在与必要的脱敏证据，不记录凭据或真实对话。
- 检查实际发出的请求体：普通对话在满足官方插件触发条件时可出现 `dsh_session_log`；无痕对话不包含该额外字段。确认正常模型消息仍按对话需要发送。
- 查明无痕对话创建子 agent 时子会话的 ID、父子归属、会话存储和日志发送路径；分别验证子会话请求及删除。不能只根据父会话 ID 推断子会话受保护。
- 如果普通对照也没有字段，先排查配置与捕获位置；此时无痕字段缺失不能算通过。若发现泄漏或无法确认归属，修复或明确限制，并补对应自动测试。

验收：实际请求层的无痕、普通对照结果可复现；子会话有明确结论。若子会话不能安全支持，需在产品中限制或向用户明确提示，不能默认为已保护。

## P1：附件、删除和异常退出

### 3. 后台任务与删除时序

- 设计带同步信号的测试：任务明确报告“开始使用附件”和“结束使用附件”，在两者之间触发删除；用事件顺序判定，避免只靠定时采样。
- 覆盖正在读、正在写、任务失败、用户取消、重复删除与不同会话并发；核对其他无痕会话和普通附件不受影响。
- 测试删除失败时是否给出明确提示，保留尚需使用的附件；可安全清理时目录最终消失。

验收：受支持的任务在仍需文件时不被提前清理，结束后最终清理；失败路径和普通对照可复现。实际桌面与自动测试分别记录，不互相替代。

### 4. 异常退出与脱离型进程

- 使用合成文件，在隔离环境区分正常退出、强制退出、重启、后台进程仍存活四种情况。
- 先确认 DSH 实际使用的进程管理路径；检查主进程退出后子进程是否仍能访问附件，以及下次启动清理的时机。
- 若不能可靠判断进程是否结束，确定明确行为：例如延后清理并提示，或限制相关功能；不把“强制清理可能仍在使用的文件”当作通过。

验收：支持的场景下重启能清理正常残留；仍存活进程相关场景有可验证的处理方式或清晰限制，并记录到用例 M09/M11。

## P1：同一版本的完整桌面回归

先在隔离环境验证，再在真实 desktop 上执行。现有真实 profile、安装包和备份属于用户数据；按当时授权与工作台规则准备安装和回退，不覆盖现有备份。

在同一候选版本依次验证：

1. 无痕开关、发消息、真实模型回复、工具调用、会话切换和手动删除。
2. 未发送草稿、关闭后输入框和普通草稿恢复；检查当前逻辑存储及相关会话记录。
3. TXT 和 PNG 的选择、拖放、粘贴、读取；删除后临时目录消失。分别注明剪贴板来源，不把一种格式推断为全部格式。
4. 同一图片用于普通会话和两个无痕会话；删除一个无痕会话后，另两个仍可读取。
5. 后台任务、异常退出恢复与额外日志保护；每项记录实际覆盖范围。
6. 普通会话对照：正常持久化、上传附件、切换、读取，确保插件没有影响普通行为。

验收：`docs/test-cases.md` 的 M01–M12 有该候选版本的通过、失败或未覆盖记录。无法执行的项目写原因，不标通过；重大失败修复后重跑受影响项。

## P2：兼容性和使用体验

### 5. DSH 更新与自检

- 列出依赖的 DSH 内部接口，测试接口缺失、签名变化、日志注册表不可用时的行为。
- 验证自检失败时无痕开关禁用、原因可读，普通会话仍可用；同时核查服务未加载与接口变化两种情况。
- 写清已实测的 DSH 版本，不把单一版本的结果扩展为所有版本。未来升级 DSH 后至少执行自动测试、隔离启动和关键桌面用例。

验收：故障注入有结果；兼容性限制和排查方式能在文档中找到。

### 6. 整理界面与文档

- 核对无痕开关实际位置，按已有需求评估能否紧跟“标准模式”；以不破坏普通模式为前提。
- 检查标识、删除确认/失败提示、无痕关闭后的状态，以及键盘操作。
- 基于实测更新 README、版本变更记录和测试清单；修正旧路线图中已过时的阶段描述，保留有价值的历史证据。

验收：用户能看懂如何开启、删除及适用边界；文档描述与候选版本的实际行为一致。

## 发布前检查

- 自动测试和隔离验证通过；桌面回归结果完整记录。未解决问题按影响判断是否阻塞预览版，重大隐私或数据损坏问题不带病发布。
- 检查差异、全部待推送提交、已跟踪文件与发布包，避免包含凭据、个人信息、真实对话和测试资料；保留普通对照数据，不误删用户文件。
- 写清版本号、预览性质、变化、安装与回退方法、实测范围和已知限制；安装包使用新版本号。
- 推送、打标签、发布及安装到真实 profile 按各自授权执行；上传代码不等于已安装或已完成实机验收。

## 每一步怎样积累测试

- 每个新增功能或发现的问题，先在 `docs/test-cases.md` 找已有编号；没有再新增。记录操作、预期、实际、日期、版本、环境和证据位置。
- 能稳定自动化的逻辑补到 `tests/`；真实桌面或请求验证保留复现步骤和普通对照。
- 修复 bug 时先复现，再修复，再证明对应回归测试能发现问题；不要把测试数量当成覆盖率或质量的保证。
- 每次迭代只跑直接受影响的测试；候选版本交付前跑完整自动测试及上述桌面清单。

## 推荐执行顺序

先做 P0 的真实请求和子会话验证，再处理 P1 的附件生命周期，随后对同一候选版本做桌面回归；最后处理 P2 和发布准备。每完成一小步就更新测试记录，遇到阻塞时先保留证据、说明影响，不为了赶进度跳过验收。
